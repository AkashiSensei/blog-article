Web 平台 CLI 工具开发的诸多问题、思考和决策

最近在给我们的 [Crater 平台](https://github.com/raids-lab/crater) 开发 [CLI 工具](https://github.com/raids-lab/crater/tree/main/cli)，虽然现在可以很快借助 vibe coding 产出一个能用的工具，但作为学生，我更希望把它做得好一些：至少学到一些东西、积累一些经验、沉淀一些思考，而不仅仅是给需要它的人交出一个产品。

当然，我们也不可能一开始就考虑得面面俱到、把架构设计得多么优雅，但至少可以把想到的问题想清楚，尽量做好一些，同时避免过度工程化。

先介绍一下背景。这个平台是一个包含 Web 前后端的加速卡集群管理平台，方便用户（主要是 AI 研究者）快速地使用集群里的计算加速硬件来跑训练或推理，助力科研。现在，用户们有使用 Agent 操作平台，或是把常用的操作脚本化的需求，这将大大提高大家的工作效率。

在这样的背景下，我们准备开发一个 CLI 工具，一方面是方便大家的 Agent 直接使用平台，另一方面也给习惯于 CLI 或者脚本的同学使用。因此在开发 CLI 的同时，不仅要考虑用户友好，也要对 AI 友好。

从整个系统架构上来说，这个 CLI 工具和前端在相同的位置上，通过 HTTP API 连接 Web 后端。

一部分问题参考了[飞书 CLI](https://github.com/larksuite/cli) 的方案，在此表示感谢。

我刚刚（距离文章发布应该有一段时间了）用 11 个 Commit 搭好了 CLI 的基本框架；目前的改动还局限在 CLI 目录内，没有为了给 CLI 铺路再去专门改后端等部分。

先总结和沉淀一下到现在为止思考的一些问题。

这篇博客可能会很干、很硬，阅读体验一般。它主要写给有经验的开发者看，基础概念不再展开。

# 总体设计

![cli-arch](img/cli-arch.png)

这里先给出一张现阶段的架构图，让大家有个大概的认识和了解。在之后的阅读中，可以了解到其中的各个模块和各个设计是怎么来的。

## 是否需要独立仓库

Crater 作为开源项目，有自己在 GitHub 上的仓库，前后端、文档网站、Helm Charts 都作为子目录放在了这个仓库里，因此 CLI 工具也作为一个子目录放进来是挺自然的事情。

作为子目录的优势大概有：
- 方便对齐版本，尤其是 API 版本
- 集中管理，维护成本更低
- 符合现在项目的组织方式
- 方便复用主仓库一些现有的工具比如 `pre-commit-check` 脚本、GitHub Copilot code review 指令

劣势大概有：
- PR 容易打架，合并等待时间较长
- Skills 的分发不太直接，路径比较复杂不好看，但其实没啥影响（之后会说）

总的来说，CLI 放在主仓库子目录、不单独开仓库，对我们当前阶段利大于弊。

## 命令组织方式

这并不是可以想当然的事情：我们要认真设计 Crater CLI 的命令结构，也就是如何分层组织子命令、命令组与参数。它既要符合人类用户和 AI 的思维与使用习惯，也要方便、优雅地组织各命令在代码里的归属。

根据我使用各种 CLI 工具的经验，大致有以下三种主要的命令组织方式：

- 动词优先：例如 `kubectl`。先说动作（`get`、`describe`、`apply`），再说资源类型和对象。
- **名词优先**：例如 `docker container`、`docker image`。先说操作哪类对象，下一级再是具体动作（`ls`、`rm`）。
- 混合：例如 `git`。顶层既有偏动词的 `clone`、`pull`、`commit`，也有偏名词的 `branch`、`remote` 等。粗看动词类入口更多，更接近动词优先；也可以理解为不少常用名词层级被压缩或省略了（例如 `code`、`staged` 等），名词维度相对收敛。

对于 Crater CLI，它本身就把资源和实体分为了很多个模块，比如资源管理、作业管理、账户（一种资源调度分配队列的表现形式）管理、镜像管理、统计数据等等，后端代码也根据模块进行组织，这天然适应名词优先的命令组织形式。

在源代码管理和 Agent Skills 开发上，名词优先也没有明显劣势，甚至更好对齐模块边界，因此最终采用了这种方式。

当然，在此之上，最好还能给一些常用的命令提供 shortcut，例如 `docker ps`（`docker container ls`）。

## 文档驱动

Crater CLI 作为这个 vibe coding 时代下诞生的子项目，我完全不认为它的代码会由人类手工完成，因此一开始就要把它做成适合 AI 开发的形式，并假定操控 AI 的人类开发者不熟悉这个项目的架构，甚至可能没看过项目的代码。

我们需要一套机制，能够在这样的背景下，确保 AI 写出来的代码符合架构设计，满足项目约束，而不仅仅是实现某个功能。并且还需要尽量降低对于开发者的要求，不要求他们熟悉 CLI 代码架构，不要求他们有很高的技术追求，不要求使用指定的 AI 工具，只要求他们遵循最基本的开发流程即可。

目前很多 AI 工具都支持仓库级或目录级的规则、提示词，但业界并没有一套统一格式；若要为每种工具各维护一套提示词，成本高且容易漂移。更稳妥的做法是用 Skills 把流程固化下来——我也正准备为整个项目（不止 CLI）补一套开发用 Skills。

但是在项目初期，规范和约束可能迭代的比较快，把它们都放在 Skill 中似乎并不合适。另外有些文档也需要人类开发者过目，这样的话放在 Skill 中就更不合适了。

于是经过综合考虑，我决定把 CLI 设计成文档驱动开发的模式，通过几个核心的文档控制 AI 开发的整个流程。具体包括架构、规约、指令和审查四个文档。目前除了审查文档均已实现，之后我会补充这个文档。开发 Skills 和 PR review 指令将会要求读取对应的文档。

具体来说，这些文档承担着以下的职责：
- 架构：阐明 CLI 的核心架构设计以及这样设计的原因，各个模块以及代码的职责，方便人类开发者熟悉项目，方便 AI 从更深层次的意图和设计上理解需要其遵守的规约背后的原因。
- 规约：阐明 CLI 开发的标准流程与约定，便于 AI 快速而高质量地完成本项目的改动。
- 指令：详细约定指令的功能、参数、行为、错误处理和边界条件等，方便人类开发者、AI 与 reviewer 对齐代码行为。要求在每一个提交中，该文档必须与实际的代码一致。
- 审查：明确 CLI 代码与文档更新的审查流程，方便 AI 工具、人类 reviewer 以及各种自然语言驱动的审查机制检查 CLI 目录下的变更。

# 构建和分发

## 编程语言

用什么编程语言呢？

- **Go**：编译成单一二进制，零依赖，交叉编译一条命令搞定，性能好启动快，CLI 生态成熟（Cobra/Viper），学习曲线平缓，而且项目后端现在用的就是 Go。
- Rust：单二进制、零依赖，性能极致，CLI 标杆工具多（ripgrep、fd 等），类型安全但学习曲线陡，编译时间长；二进制体积与依赖、链接方式有关，未必总比 Go 小或大。
- TypeScript/Node.js：与前端同语言可复用类型定义，npm 生态丰富，但需用户先装 Node 运行时，打包后体积大（几十 MB）。
- Python：CLI 生态好（click、Typer），但需 Python 运行时，打包成可执行文件简直是地狱。

得益于一堆现成的 TUI 组件库，TS 在现在的 TUI 程序比如 Claude Code、OpenCode 中使用非常广泛，但是并不完全适合 Crater CLI。我们没有那么复杂的前端交互需求，甚至对于我们的场景来说这是负优化，不如 Go 的单一可执行文件更能让用户省心。于是决定使用 Go 了。

## 分发（ToDo）

主要有 macOS、Linux 和 Windows 的用户，如何分发这个 CLI 工具呢？既要能方便用户安装，又不能增加太大的维护成本。

主要考虑以下这几种方式：
- **npx 式的一键安装**：类似于 Codex 和飞书 CLI 的做法，通过一行 npx 命令 `npm install -g @larksuite/cli` 即可完成安装。对于用户，需要已经安装好 npx，AI 时代下大家基本都有；对于开发者，需要注册 [npmjs](https://www.npmjs.com/) 账号，然后发布包，也比较方便。
- **GitHub Release 下载**：用户直接从 GitHub 网页下载二进制可执行文件。这里需要区分一下 GitHub Packages 和 GitHub Release，前者主要用于包、镜像等等，这是我们现在发布前后端镜像使用的方式，由集群的 Kubernetes 拉取；后者是发布给用户方便浏览器下载的可执行文件和附件。对于用户，这需要用户自己访问 GitHub 并根据自己的平台下载；对于开发者，只需要在 Workflow 中向 Release 上传即可，类似于我们现在向 Packages 推送镜像的做法。
- 包管理器：比如 Homebrew 甚至 apt，虽然用户安装起来很方便，但是用官方源的话，开发者侧审核和维护比较费劲。

计划先提供前两种方式，也就是通过 npx 和 GitHub Release 分发。

## 更新与版本管理（ToDo）

一开始先别做得太复杂：分发和版本先交给现有成熟工具，Crater CLI 内部暂不实现自更新等能力。即便要做，受网络环境影响，程序自己去 GitHub 拉版本信息也会很折腾。

细想之下，版本管理里还有不少坑，尤其是 GitHub Release 与后文会提到的 API 版本问题。一个 Release 必须挂在一个 tag 上，tag 又指向某次提交；tag 不宜频繁挪动，而主干上的最新提交却在持续前进——于是很难既「优雅」又高频地发 CLI 版。这需要单独拿方案在团队里对齐，把流程理顺，必要时对主仓库做一轮重构与规范，甚至值得另写一文。本文后半只会稍微展开其中一部分，不承诺给出完整答案。

# 状态与存储

需要思考：如何像浏览器缓存那样缓存用户的数据，例如 access token 等等。

CLI 进程本身是无状态的：每条命令都是一次独立运行；若不借助外部持久化，CLI 既无法在内存里长期保留状态，也无法记住上一条命令留下的结果。

一旦要做持久化，就几乎一定会碰到「存哪儿、怎么存」的问题，也就绕不开跨平台差异。

基于此，有一些问题和思考。

## 用户数据缓存

Crater 的设计本身是有状态的，比如对于同一个当前登录的用户，需要记录当前激活的身份（普通用户还是管理员），以及激活的账户（资源调度分配队列的表现或抽象），以及一些用户基本信息，这些都需要随请求发送给后端。

不可能让 CLI 每条命令都重新登录、重选身份和账户，因此必须在本地持久化这些信息。

存储系统是一个保存这些信息非常棒的地方，但是需要处理不同平台上路径以及解析的差异。`os` 这个 Go 包提供了获取配置目录的函数 `os.UserConfigDir()`，负责处理不同平台的配置路径差异，然后 Crater CLI 在其中存储自己需要的数据即可。

语言等其它 CLI 设置也可以一并放在同一配置目录下。

## access token 的保存

区别于一些普通的状态或缓存数据，这些数据可能有加密需求。虽然目前使用的是和 Web 端一样的 token，可以直接从浏览器缓存中拿到，但我们在 CLI 的设计上还是将其加密存储。

各个操作系统提供了相应的凭据存储服务，敏感的数据由这些系统组件保管和加密。

对于 Crater CLI，只需要使用 Go 语言提供的第三方包 `github.com/99designs/keyring`，让它充当一个适配层的角色，来访问不同系统提供的凭据存储功能。

Crater CLI 允许用户用多个身份登录某个 Crater 站点，或是登录多个 Crater 站点，因此会保存多个凭据。目前以站点、用户名、登录方式为键存储这些凭据。

## 登录与鉴权

登录流程怎么设计，同样值得单独想清楚。

目前 CLI 采用的是和前端一致的，明文传输密码的方式，没有在请求后端之前就加盐加密，也就是说后端会拿到用户实际的密码，当然现在至少没有明文存储。

这其实不是一个好的方式。至少后端不应该能够拿到明文的用户密码。

在通过 CLI 登录时，可以交互式输入密码，或者在命令中使用 `--password` 选项直接提供。这种实现更烂了（

更好的方式是在后端实现一个安全性更好的登录接口，然后前端登录时弹出一个链接或者二维码，让用户通过各种方式安全登录，CLI 全程只拿到一个 token，不经手用户的密码。

之后再考虑做吧，或者简单的功能丢给学弟学妹做，目前还没有修改 `cli/` 目录之外的任何内容。

此外，还需要考虑的一点是，我们或许最好在 Header 中补充上应用信息，让后端能够判断请求来自于 CLI 还是 Web 前端。目前这可能是个伪需求，因为并没有什么功能可能会用到这个，除了 CLI 的开发阶段，可能使用白名单限制 CLI 登录。

# 接口与网络

Crater CLI 的一切功能，都是建立在 Crater 后端 HTTP API 的基础上的，与之死死绑定密切相关。基于此又有一些问题和思考。

顺带一提，很不幸的是，目前前后端 HTTP API 正在进行大规模重构，使其符合 RESTful 标准，并形成一些 Crater 专有的约定，比如一些专有的业务错误码，还一些之前不规范开发的技术债。这将会对 CLI 的开发带来巨大的影响。

## API URL 结构问题

Crater CLI 工具不应该只能访问部署好的 Crater 服务，还应该能够连接通过代码运行的开发版本。这样的开发版本可能有不同的 API URL 结构或者前缀，因此最好能够支持配置。

目前 Crater 开发和生产环境的 API URL 结构实际上是一样的，不过我们还是以一个比较优雅的方式整理它们比较好。

使用统一的 prefix，与各个命令的 path 拼接成为完整的 URL。

## 代理问题

注意到许多 CLI 工具在检测到代理时会产生警告，这使我注意到这个问题。

我们实验室内部的 Crater 服务部署在内网中。用户在学校的其他地方或者在校外都需要使用 Easy Connect 来访问，同时一般还需要使用连接外网的代理软件。虽然这不是 Crater CLI 该考虑的问题，但作为开发者，我们需要保证 Crater CLI 能够在这样的环境下运行。

CLI 使用 `github.com/imroc/req/v3` 构造 HTTP 客户端，其底层的 Transport 在创建时把 `Proxy` 设成了标准库里的 `http.ProxyFromEnvironment`，其行为与 `net/http` 一致，也就是跟随诸如 `HTTPS_PROXY` 这样的环境变量。

经过我在 macOS 上的尝试，在代理环境下它可以正常工作，那也就不折腾了。

也没有计划提供让用户填写代理主机和端口，CLI 去连接的功能。

## API 版本管理（ToDo）

不仅仅是 API 的版本管理，Crater 的版本管理也需要优化一下，目前刚刚只有 `v1.0.0` 一个正式版。

首先来讨论一下 API 的版本管理。

CLI 的运作依赖 HTTP API，如果版本发生变更，导致某个接口变更了或者没了，那么 CLI 很可能无法成功执行，并产生奇怪的错误。集群管理员部署的 Crater，与用户给自己安装的 Crater CLI 的版本更新大概率是不一致的。可能集群每天拉取 latest，或者每个新的 Minor 版本发布后将集群更新到上一个版本。但是与之相对的，用户自己安装的 Crater 可能 8 年（夸张）都不会更新。

这就产生了矛盾，很可能会有版本不一致的问题。

处理这个兼容性是一个系统工程，需要考虑代码实现、开发约束等等各方面的内容，大概想了想会涉及以下内容：
- CLI 客户端本身的开发规范：例如允许没见过的响应字段，不强制检查，兼容 API 新增返回字段的情况。
- 接口的开发规范：不删除，只新增，甚至不修改。接口的修改考虑到兼容旧版本的请求，实在不行直接新增一个 v2 版本的接口，保留原来的让旧客户端访问。
- 版本握手：提供一个客户端与后端进行版本握手的功能，让后端判断是否会有 API 不兼容的问题。实现这个是必要的，但是这个实现起来又会有更多的问题：
- API 对于各类消费者的友好程度：除了前端和 CLI，这套 API 还有其他的消费者，比如正在作为本科毕设被开发的一套智能运维和 AI 助手功能。不同的接口对于不同消费者的友好程度是不一样的，它们可能设计的不是很好，返回一个格式化后数万行的超长 JSON 之类的，前端或许可以接受，但对于可能需要直接暴露完整响应的 CLI 非常不友好。
- 同时支持重构前后的两套接口：之前提到，目前的 API 还在进行规范化的重构，这是一个逐步进行的过程，也就是说 CLI 需要在有一段时间内兼容重构前和重构后的接口。

可能看起来很奇怪，但实际上就是要解决各种各样交织在一起的奇妙工程小问题。直面用户的需求，积累解决这些问题的经验，恰恰是这些项目的价值所在。

这里显示的 v1.0.0 就是 tag 触发的构建注入的版本号，但是在这之后由主分支更新触发构建的版本，还并不能意识到自己是 v1.0.0 之后的某一个版本。

遗憾的是，我们现在还没有一套完整的方案，等重构 API 的 PR 更新之后，得抽时间整这样一个方案，然后上会讨论一下。

## 访问控制（ToDo）

CLI 工具还有一个问题，它大幅降低了用户提交作业或者申请资源的时间成本。

现在有些用户有很多任务需要跑，或者排不到卡时可能会创建数十个作业来排队或者泄愤，如果有了 CLI 工具，就可以很方便地在 1 秒内提交成千上万次请求。

虽然我们现在为作业队列添加了接纳控制，限制用户提交的最大作业数量，但是频繁的网络请求依旧会影响大家的使用体验。虽然这样的情况可能比较极端，但是本着为用户负责的态度，最好还是要在 CLI 工具层面避免这种情况出现。

或许可以记录用户上次操作时间，或者近几次的操作时间，来限制 CLI 的操作频率。或者更简单的，针对提交作业的操作添加 1s 的延迟，再通过一些锁的机制，来避免有多个 CLI 客户端同时运行发起请求。

# 测试

Crater 原来其实就是没有自动化测试的，只有一些基本的 Lint 和构建测试，而没有检查功能的单元测试。这在大家普遍用 AI 写代码的当下，可能显得有点不够了，功能正确性基本都建立在大家的水平和 AI PR Review（关于这个可以看我[另一篇文章](https://zhuanlan.zhihu.com/p/2037582638454682241)）的能力上了。

于是，我认为添加一些自动化的测试机制是非常有必要的。它最好能够实现这些目标：
- 尽量保证 AI 写的功能是符合预期的
- 保证 AI 实现新功能的时候没有破坏旧的功能
- 方便 reviewer 审查

基于此，有一些测试上的思考和设计。

## 单元测试

这是 Go 里面最基本的测试，Go 对其有比较好的支持和体验优化。

我们约定，让 AI 在实现功能的同时，或者实现功能之后，给关键和核心的功能添加单元测试，在提交之前和 Workflow 中测试这些基本的逻辑。

通过这种方式，在一定程度上确保 AI 写的功能是符合预期的，并不会破坏已有的功能。

## 快照测试与测试沙箱

上面创建的单元测试有以下特点：
- 不方便看测了什么：测试用例写在代码里，人类开发者和 reviewer 并不好检查都进行了哪些测试，判断测试覆盖率是否足够
- 不方便看预期结果：测试用例的输出和结果不太明显，人类开发者和 reviewer 并不好确认 AI 设定的“符合预期的结果”是否符合自己的预期
- 与实际使用体验没有对齐：单元测试的测试主要是针对内部的逻辑，并不是测试实际的命令输出，也就是说与用户实际的使用场景并没有对齐

现在人类开发者和 reviewer 实际上很少会仔细看 AI 写的代码了，在这样的背景下，结合上述单元测试的特点，我认为只有单元测试是远远不够的，无法保证交付到用户手中的产品是符合需求分析和开发团队预期的。

因此，我打算引入和设计一种快照测试机制，具体来说，我对它有如下期待和需求：
- 能够把命令实际的输出和命令本身纳入版本管理，提交到仓库中，方便在 PR 中直接检查
- 开发者能够方便的在自己的开发环境中运行这个测试，生成自己新命令的快照，并检查是否破坏其它命令的快照
- 可以在 GitHub Workflow 中运行
- 测试不应该对实际的用户环境和生产集群产生影响

但是想要实现，还有许多的问题需要解决和处理：
- 不同开发者的系统环境是不一致的，开发者们可能使用不同的操作系统、可能选择了不同的语言等等，这都会导致输出不稳定
- GitHub Workflow 的环境可能又与通常的开发环境不同
- 用户的登录状态和集群状态是不稳定的，比如一个查询当前登录用户信息或者排队作业列表的接口，其输出对于不同开发者、不同时间、不同目标集群都是不稳定的
- 目前没有在互联网上可访问的专用测试集群

为了解决这些问题，满足我们的需求，我们需要针对我们的场景，设计一套快照测试机制。

在我们的场景下，实现一套太过于完善的测试机制也完全没有必要，可以牺牲部分用例来简化实现的难度。比如可以不连接真实的集群测试实际的网络请求，主要以失败的用例为主，检查错误处理逻辑是否足够完善。

经过综合考虑与权衡，我最终设计并实现了一套初步的快照测试和沙箱机制。

目前 Crater CLI 对于环境的访问主要包括：
- 读环境变量
- 读写文件系统：包括前述的 Keyring 和非加密数据
- 读写网络资源：通过 HTTP API

我们保留环境变量读，用它来控制 CLI 的一些行为，但是对文件系统和网络资源提供一种隔离的方式。

具体来说，为文件系统的读写和网络请求提供各自一套虚假实现，通过环境变量进行控制，在测试环境中，避免对文件系统和网络资源的读写。对于文件系统读操作，比如检查当前登录的用户，直接返回一个虚假的数据，而不实际调用相关的库读取文件系统；对于写操作，则可以返回一个假成功，也就是实际上什么事情都不做，但是认为操作成功了。对于网络操作，则直接返回网络超时或者 404 Not Found，对于关键的接口，也可以注册对应的假实现来返回更加像真实数据的模拟数据。

从实现上来说，我们需要将文件系统的读写和网络请求收窄和集中，提取访问文件系统和网络的工具或入口，并约束必须通过这些接口访问，避免对二者的访问分散在代码的各处。然后对这个入口和工具进行处理，使其能够读取相应的环境变量或是构建参数，使用这套沙箱的文件系统和网络访问实现来进行模拟，而不真的访问开发者或者环境实际的文件系统和网络。

至此，我们便提供了一套能够实现隔离的机制，接下来还需要实现快照的机制。

保存下来的快照文件需要满足：
- 人类可读，方便人类 reviewer 检查
- 易解析，方便做 diff 判断实际运行的结果和旧的标准（称之为 golden file）是否一致
- 明显是生成的结果，不要引起“我可以手动修改或者创建它”的误会

当然，实现一个我们自己的文件格式以及其解析和编辑工具能很好的解决这些问题，但是现阶段显然没有这个必要。

直接使用 Markdown 可能会带来一些误会，例如让不熟悉的开发者尝试自己新建或者修改它。我找到了一个比较合适的工具，是官方工具链里的 `golang.org/x/tools/txtar`，它能把多个小文件打进一个文本文件。使用它，我们就可以把命令的 stdout、stderr 和退出码等信息逻辑上分散在多个文件中，互不干扰，方便定位和查找，但是物理上在一个完整的文件中，方便人类可读。例如这是一个文件中一个测试留下的快照。

```
-- en/01-missing-platform-nojson/argv --
crater auth login --no-interactive --username u --password p
-- en/01-missing-platform-nojson/exit --
2
-- en/01-missing-platform-nojson/stdout --
-- en/01-missing-platform-nojson/stderr --
Error:
  platform URL is required (--platform)
```

![make-test](img/make-test.png)

当然，还要为之提供配套的 make 目标，这样我们就可以在仓库中留下命令执行的稳定快照了。

![pr-comment](img/pr-comment.png)

在 review 时，reviewer 就能直接对命令的输出（主要是错误流程）提交评论了。

# 人文关怀

CLI 工具并不仅仅打算给 AI 和脚本使用，还需要照顾到习惯用 CLI 的人类用户。

## 命令提示与多语言支持

一方面我们实验室的内部用户就有不少母语非中文，另一方面作为一个开源项目，我们也应该做一些国际化的努力。

Crater 的前端目前支持中、英、韩、日四种语言，于是我决定让 CLI 至少支持中英两种语言，先把框架搭出来，之后接入更多的语言也方便一些。

我们使用了一个非常轻量级的自研包来支持多语言的切换，在代码中注册各个命令中英文的描述等信息，实际执行时根据用户设置的语言展示渲染对应的文本。

为了避免有翻译键的缺失，还需要为其补充上测试机制，遍历命令检查是否有缺失的翻译键。这个现在还没有做。

![help-message](img/help-message.png)

此外，为了给用户带来更好的使用体验，我们使用了 Cobra 来把命令行程序组织成子命令树，并使用其原生提供的功能展示各级命令的帮助信息。这很符合用户的使用习惯，但会有个小问题，输出的帮助信息的框架依旧是英文的，虽然我们也可以修改它的语言，让它也随设置的语言变化，但我认为没有必要。

## Tab 命令补全

Tab 补全同样是一个非常常用的功能。比如我就很依赖 Tab 补全，不仅靠它补全已经输入了一半的命令，更依靠它查找需要的子命令和选项。

Tab 补全是一个 Shell 侧的功能，由给当前软件注册的 Shell 脚本来处理用户当前输入，生成候选输出，再交给 Shell 的脚本来补全或者展示候选。如果生成候选的逻辑比较复杂，也可以让注册的 Shell 脚本调用二进制程序生成候选，这在实现复杂逻辑时更加的方便，并且其带来的性能开销在现在的计算系统中完全可以接受，目前我们就采用的这种方式。

显然，不同的 Shell 表示输入和展示候选的逻辑都不太一样，需要注册的补全脚本也不太一样。目前我们提供了对 Bash 和 Zsh 的支持，之后考虑提供对于 Pwsh 和 Fish 的支持。

Crater CLI 在二进制文件中实现了一个补全引擎，用来为用户输入生成候选；为不同 Shell 提供了适配器，用来解析不同 Shell 提供的不同格式的用户输入，并把候选输出处理成 Shell 能够解析的格式。并把这个补全功能做成了一个隐藏命令，方便 CLI 为不同 Shell 注册的补全脚本调用。这个隐藏命令有自己的快速通道，不解析通用的选项，不构建完整命令树，并约定无特殊情况不访问文件系统和网络，以实现比较低的补全延迟。

同时，这个补全系统还允许开发者给自己的命令本身及其选项注册专用的补全函数，用于动态的生成候选项或者描述。比如在切换当前账号时根据已保存的凭据提供候选，或是在提供切换语言的候选时显示当前的语言。

此外，用户可能有不同的命令书写习惯，比如把全局选项放在子命令前，抑或是把全局选项放在整条命令的最后，我们的补全都应该能识别。

说回为不同的 Shell 注册补全脚本的问题，比较常见的做法似乎是把补全的逻辑放在一个专用的脚本文件中，然后在用户的 .zshrc 中引用它。但是我们的环境比较复杂，可能涉及到把分布式存储中用户的文件挂载到容器中的情况，因此如果再让多个文件协作支持补全的话，可能会带来更复杂的问题，于是决定把所有支持补全的 Shell 侧需要的工作，全部放到用户的配置文件中，因为核心逻辑都在二进制程序中，这个脚本的行数也不多，完全可以接受。

## 命令交互

对于人类来说，即使有 Tab 补全的支持，也不太好让大家一口气写出包含很多选项的长命令，于是我们引入通过 TTY 和简单的 TUI（`survey` 库）来实现与用户简单的命令行交互，包括引导用户逐步输入用户名密码，允许用户在已经登录成功保存下来的凭据中选择要激活哪个等。

不过这些主要还都是为了尝试，主要是为了支持用户在使用 CLI 提交作业时，能够交互式的查询、选择加速卡，搜索和选择使用的镜像等等。相信对于人类来说，这种方式要比看到完整命令报错再一点一点修改的效率要高很多。

除了输入，还有输出，输出也是用户使用体验的重要一环。为了避免不同命令的输出出现漂移，我们同样在代码中设置一套机制统一处理输出和报错。具体来说，制定了一些 CLI 错误类型，并将其映射到退出码，然后提供相应的接口、规范和工具函数，让开发者能够快速标准的将成功的输出信息或是错误原因呈现给人类用户以及 AI。

![multi-error](img/multi-error.png)

对于有很多个选项的命令，比如登录命令和之后的创建作业命令，如果有非法参数或者错误参数，一个一个报错，让用户一个一个修改是效率非常低的方式。此时我们需要先尽可能的检查每一个参数，收集每一个错误，然后一次性统一报告，而不是遇到问题直接报错退出。

![mulit-together](img/mulit-together.png)

看起来像这样，尽量让用户和 AI 一次性看到所有的错误并修改，避免浪费用户的时间和 Token（这里指词元而不是前文中的登录凭据）。

# AI 友好

相比于人类，各个 AI 可能是我们更直接的用户。

## 禁用交互式模式

目前市面上的 AI 工具有很多，不是所有 AI 都能够交互式的使用命令行工具。从标准输入输出，到 TTY，再到 TUI，对人类的支持越来越好，但是给 AI 用的难度却越来越大，尤其是在各种各样的沙箱环境中。而且对于 AI，本身也没必要使用交互式功能，直接通过 -h 查看用法，然后给出一个超长但准确的命令反而更加直接和高效。

![no-interactive](img/no-interactive.png)

为此，我们专门提供了“禁用交互”的全局选项，主要面向 AI。所有的命令（除了补全使用的隐藏命令）都支持这个选项。当激活这个选项时，如果命令本身就没有交互式的话那么什么都不会发生，如果有交互的话，那么将停用交互，使用另一套完全不交互的逻辑。以登录命令为例，当通过选项指定目标平台和用户名后，如果不禁止交互，命令会提示用户输入密码，然后尝试登录；但是如果指定禁用交互，那么命令会直接报错退出，并提示需要提供密码。当然这是个不太安全的登录方式，这里仅仅作为示例说明禁用交互式选项的工作方式。

## JSON 原始输出格式

另外，考虑到相比于自然语言，AI 能够更准确的理解 JSON 这种结构化的语言，因此我们还提供了 `--json` 全局选项，开启这个选项后，默认开启禁用交互选项。这个选项会让命令的输出变为可解析的 JSON 格式，方便 AI 工具更准确和直接的理解。对于一些 GET 请求，它很可能会直接返回信封包装后的响应，而不是为了让人类看解析成自然语言，再让 AI 通过自然语言重建原始信息，这反而不太直接，并且可能会带来信息失真。

![json-error](img/json-error.png)

除了成功输出，JSON 模式下的报错也会以 JSON 形式提供。这里需要注意的是，如果用户使用了 JSON 模式，但是写错了命令，此时如果不做处理的话，很可能会由于目录树解析失败而 fallback 到命令错误输出上，常见的比如直接显示 help 页面，或者用自然语言提示用户查看 help 页面，这其实破坏了 JSON 模式下输出为 JSON 的约束。于是在命令解析之前，我们会先扫描 JSON 选项，将其视为一个比较强的约束，当命令解析失败时，也不让它 fallback 到设置的错误命令提示上。

![json-help](img/json-help.png)

飞书 CLI 的输出基本上都是原始的 JSON 形式的 HTTP 响应，也许是觉得这种方法好，也许是觉得这样方便和简单，但总之我参考了它们的设计。

## Skills 的组织与编排

虽然 Crater CLI 是基于文档开发的，其中包含对于包含了哪些指令及其具体行为的完整描述，但是这并不足以让 AI 使用 Crater CLI，因为这还不能让 AI 理解 Crater 的专有名词，不能让它理解用户需求，更不能让它把自然语言表达的用户需求准确的映射到指令上。为此，我们需要通过 Skills 教 AI 如何使用 Crater CLI。

本质上都是文本形式的提示词，为什么选择 Skills 呢？我认为是因为它是不同 AI 工具通用的，同时相比于直接提供完整文档，Skills 更节省上下文。

![skill-context](img/skill-context.png)

在实际解决问题过程中，宿主也就是 Cursor 这类 AI 工具，会把已经启用的 Skills 整理成可用技能列表的形式提供给背后的大语言模型，列表项主要包括 Skills 的名称、简要描述和路径，帮助模型做 Skills 发现。当用户引导或模型决定使用某 Skills 时，模型才会读取完整的 Skills，然后按其中步骤执行。

这个机制的正常运行依赖合理的 Skills 组织方式，否则如果把所有内容全塞在一个 Skill 里面，那么这个机制将完全报废。这也就引出了我们的问题，只有以更合适的方式组织 Skills，划分好不同 Skill 的职责，写好每个 Skill 的描述，才能让模型更精准的读取需要的功能。

那么具体应该怎么组织 Skills 呢？我也没有经验，我也不懂是不是应该按用例组织 Skill，还是应该按模块或者域组织呢，或者是什么其它或者交叉的方式？于是参考了一下飞书 CLI Skills 的编排方式，他们基本上是按不同的产品组织的，比如飞书文档整理成一个 Skill、飞书云盘整理成一个 Skill，每个产品中的 Skill 中包含了许多的子文档，说明各个产品的各个功能该如何使用 Skills 使用。飞书 CLI 也是采用名词优先的命令组织方式，但是和我们不太一样的是，我们的 Crater CLI 的命令更贴近自然语言，而飞书 CLI 的命令更加贴近于 API 本身，这对 Skills 的依赖也会更强一些。

也就是说，由于飞书 CLI 第一个子命令与产品对应，也就是说实际上相当于一个子命令对应一个 Skill，除此之外还有一些负责整体流程编排和引导的 Skill。

回到 Crater CLI 上，我认为采取类似的模式，大致一个子命令对应一个 Skill 是比较合适的，既不会导致 Skills 过多，也不会导致每个 Skill 过于厚，同时由于模块的划分是比较清晰的，AI 可以快速通过模块找到需要的 Skill，对于一些跨模块的任务，也可以通过描述和编排 Skill 引导。

![arrange-skill](img/arrange-skill.png)

至于这个编排 Skill 或者说共享 Skill，主要用于处理一些 Crater CLI 共享的知识以及跨模块的流程问题。比如如何使用全局选项，它们有什么功能；CLI 有哪些错误码，导致这些错误的可能是什么问题，怎么去排查这些问题等等。

## 如何写好 Skill

接下来进入到具体每个 Skill 该怎么写的问题上，当然最终肯定还是 AI 写，不会像这种博客一样我一个字一个字手搓，但是人一定要把总体方向和关键方法。

这也是一个很大很大的话题，我并没有仔细研究和学习过，这里只根据我接触到的一些资料和经验进行简单的总结。

首先 Skill 的 YAML front matter 中需要包含如下信息。

- `name`：Skill 的唯一标识。通常和目录名一致，方便引用和维护。
- `version`：Skill 自身版本，便于以后升级 Skill 内容、排查行为变化。
- `description`：给 AI 看的调用说明。它应该写清楚“这个 Skill 做什么、什么时候该用、典型用户说法是什么”。
- `metadata.requires.bins`：声明这个 Skill 依赖哪些本地可执行文件。

之前介绍过它们对于 AI 调用 Skill 的作用与机制，想写好 Skill，首先需要有合适的描述信息，让 AI 能够定位和使用到对应的 Skill。这里的合适，我理解为准确，避免歧义和避免重复，也就是说要准确描述这个 Skill 可以做什么，同时避免不同的 Skill 有重复的描述，让 AI 不知道选择哪个，或者不知道它们该如何配合。

此外，根据我的观察和经验，我大概总结出以下一些有助于提高 Skill 效果的 tips。

从设计上来说，Skill 描述的是一个执行的流程，但在实际的场景下，流程通常不会是完全线性的，非线性的部分往往是最容易引起混乱的地方，因此我们需要在 Skill 中明确的告诉 AI 如何控制整体的流程。比如，明确的告诉 AI，当检测到什么输出时，认为某个步骤已经完成，否则会退至哪个步骤重复执行，直到满足什么条件，或者尝试几次后退出。再比如写清楚非正常情况下的扩展流程，类似于需求规格说明书中用例的扩展流程，描述清楚出现意外状况时如何处理，例如说明当用户登录出现什么报错时，可能是什么问题，如何排查，是否需要联系管理员解决。流程上覆盖更多的场景，很可能是提升实际使用体验的关键。

还有一个问题是，用户不一定能够准确的表达自己的需求，作为开发者，我们不能假设用户熟悉 Crater 的每一个基本概念，不能要求用户有足够的云计算/AI Infra 方面的基础知识，因此，还需要让 Skill 具备识别用户的误解的能力。抛开模型本身的能力不谈，我们需要在 Skill 中补充一些这样的信息，来让它在这件事上有更好的表现，比如告诉 AI，用户可能不能理解什么什么，或者可能将其误解为什么。更进一步的，超脱于 CLI 本身的功能之外，可以专门提供一个教学 Skill，来让 AI 帮助用户理解一些熟练使用 Crater 所需的基础知识。

相比于描述要做什么，怎么做，很多时候直接给 AI 一个例子，能够让 AI 更好的照猫画虎的给出更符合我们开发者预期的命令。人也是这样，我写这篇文章的时候也是这样，提供一些例子，更能让读者理解我想表达的内容。比如提供一个真实可用的超长命令，然后告诉 AI 它该如何修改生成满足用户实际需求的命令。

最后，还要明确的写清楚哪些是做不到的，不要让 AI 认为 CLI 可能有这个功能，但是 Skill 写漏了，然后反复的进行奇奇怪怪的尝试，既可能浪费用户的 Token，还可能对集群造成一些破坏。当然，如果这造成破坏了，一定是开发者的责任，是我们没有做好足够的防护。

## Skills 的分发

这更是一个关键的问题，Skills 写的再好，也得让用户能用上，而且还得在合适的时候提醒用户更新 Skills，并且方便用户更新。

目前 `npx skills` 感觉已经是一个非常成熟的 Skills 管理方案吧，就用这个挺好。我觉得唯一的不足是 `~/.agents/skills` 似乎不支持嵌套目录或者说子目录，至少不是所有的 AI 工具都支持，这比较麻烦，不好统一的删除和卸载 Skills。
